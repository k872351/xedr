## ADR-001 主机名不作为终端身份

- **状态**：已实现（2026-11 前）
- **决策**：注册请求无 `agent_id` 时签发全新 UUID，不按主机名/IP 复用；覆盖安装保留原 token，但检测到不同服务器地址时拒绝并要求显式迁移。
- **理由**：主机名会重复（克隆机、同名办公机）、会变化（改名/域切换）、可被伪造。用它做主键会导致告警串档、策略错配、审批误下发——这类 bug 一旦发生很难追溯。
- **后果**：重装/迁移场景需要显式身份继承流程；同一台机器换服务器必须人工确认。相关实现：`backend/agent_protocol.py`（注册）、`agent/install.go`（覆盖安装）。
- **教训**：早期注释曾写「按主机名复用」，代码行为改了但注释没改，导致误判。改行为必须同步改注释。

## ADR-002 版本与策略状态持久化到 DB，不存进程内存

- **状态**：已实现
- **决策**：`sync_revision` 存 `agent_meta` 表；策略 LKG（last-known-good）与 applied/offered/bad rev 落 Agent 本地 SQLite。
- **报告数据库连接补充约束（2026-11-23）**：既有 WAL 模式不重复配置；首次设置时必须检查 SQLite 返回的实际模式，未进入 WAL 则关闭连接并报错。保留原同步参数，不将双连接事务测试当作生产故障切换或断电验收。
- **理由**：服务端重启、Agent 重启、升级回滚都必须恢复到正确版本。进程内存计数在重启后归零，会出现「服务端重启后在线 Agent 继续用旧规则」。
- **后果**：所有版本读取走 DB/文件，有 I/O 成本；换来可恢复性。相关：`backend/agent_sync.py`、`agent/policy_state.go`。

## ADR-003 策略必须验签 + 试用期 + LKG 回滚

- **状态**：部分实现（服务端签名未闭环，见 ADR-010）
- **决策**：Agent 生产默认强制 Ed25519 验签；同版本也验签并比对内容摘要；新策略进入 probation 试用期，资源超限或连续重启自动回滚到 LKG；被拒策略记录 `bad rev` 避免重试风暴。
- **理由**：策略是远程控制面，未经验签的策略等于任意代码执行入口。试用 + LKG 让错误策略不把终端打死。
- **后果**：策略下发有延迟（试用期），且要求服务端与 Agent 密钥体系一致。

## ADR-004 所有上行遥测先落盘 outbox，再批量投递

- **状态**：已实现
- **决策**：采集数据一律先写 Agent 本地 outbox（SQLite），后台发送器批量/合并投递；命令 ACK 与回执同样落盘。后端 ES 索引用持久化队列。
- **理由**：断网、崩溃、服务端重启都不能丢数据；合并（coalesce）避免全量快照堆积；回执支撑幂等。借鉴 openedr「本地缓存 + 批量上报」的可恢复遥测架构。
- **后果**：引入本地存储占用与队列上限（`box.dropped` 需监控）；换来「ES 恢复后补齐已确认事件」。
- **相关**：`agent/queue.go`、`agent/agent_loop.go:pushTimeline`、`backend/es_event_queue.py`。

## ADR-005 采集与研判分离：慢任务不进心跳主循环

- **状态**：已实现（2026-11-22）
- **决策**：心跳主循环只做快车道（HTTP 心跳、策略验签、回执记要、周期更新）；规则同步、命令执行、升级、内存扫描一律投递 `agent/slow_lane.go` 的有界单 worker 队列，同类任务合并、超时丢弃；触发式内存扫描走 `trigger_scan_queue.go` 有界队列。
- **理由**（DataProtector 架构铁律）：检测内容要能不重编 Agent 就更新；主路径被慢任务阻塞 = 心跳超时 = 终端被判离线 = 命令积压。有界队列防止慢任务无限堆积打爆内存。
- **后果**：命令执行从「同步」变「异步排队」，需靠回执/lease 重投保证不丢；`responseEnabled` 改原子、FIM 配置加锁以消除跨车道数据竞争。
- **备选方案（否决）**：直接开 goroutine 不设上限——会并发重入 `applySyncBundle` / `cmd_receipts`，且无背压。

## ADR-006 命令执行幂等：回执 + 审批单 ID 作幂等键

- **状态**：已实现
- **决策**：`cmd_receipts` 表记录 started/done；lease 过期重投的同一命令 ID 只重放 ACK 不重跑；非幂等动作（升级/隔离/杀进程/隔离文件）中途崩溃不自动重跑，改为回报失败由管理员决定；审批单 ID 作为下发幂等键。
- **理由**：网络重投是常态，处置动作重跑可能造成不可逆副作用（重复隔离、重复删文件）。
- **后果**：需要 7 天回执 TTL 清理；`verification_required` 作为「结果不确定」的显式信号。

## ADR-007 策略对账只做观测与审计，不主动推送

- **状态**：已实现（2026-11-22）
- **决策**：服务端消费 Agent 心跳自报的 `applied_rev / status / local_sync_rev / local_policy_rev`，判定 converged / behind / rejected / rolled_back / probation / unknown，异常状态写 `agent_audit`（120s 冷却）。**不改变**「心跳拉取式」下发机制。
- **理由**：现有下发是 Agent 用 `pm.offer()` 自行判断应用；服务端若主动推送会与拉取机制冲突并破坏协议兼容。观测 + 审计 + 状态暴露已能支撑管理端诊断与人工介入。
- **后果**：自愈是「发现漂移并暴露」而非「自动修复」；真正的修复仍靠下一次心跳的正常 offer 流程。
- **参考**：DataProtector `AgentSyncClient.cs`（appliedPolicyVersion + lastApplyStatus + 查内核真值）。

## ADR-008 规则回放直接调 matcher，不走 pipeline 后处理

- **状态**：已实现（2026-11-22）
- **决策**：`tests/rule_replay/run_replay.py` 直接 `importlib.import_module(f"backend.matchers.{name}").run(report, store, set())`，断言 `rule_ids / titles_any / min_severity / max_findings`。
- **理由**：实测 `analyze_report(only_matchers=['keywords'])` 的 `findings_aggregated` 为 0——pipeline 的 `_merge_partial` / `prune_inactive_modules` 会过滤掉局部重跑结果。直接调 matcher 既复用生产同一批规则，又不受后处理影响，且**不改 pipeline**。
- **后果**：回放覆盖 matcher 层，不覆盖 pipeline 聚合层；这是有意的边界，避免为了测试改生产逻辑。

## ADR-009 多信号风险评分为「就地丰富」，静态分作下限

- **状态**：已实现（2026-11-22）
- **决策**：`backend/risk_scoring.py` 是进程内、带锁、随时间衰减的评分累加器；事件 detail 就地补 `risk_score / risk_level / risk_breakdown / risk_tactics`。展示分取 `max(静态规则分, 累计分)`，不倒退。
- **理由**：事件落库已包含 detail JSON，就地丰富无需改表结构、无需新增列；静态分作为下限避免评分衰减/重启归零时历史告警看起来「变轻」。
- **后果**：评分状态重启后从零开始（与「风险会衰减」一致）；跨重启的长期风险画像需要持久化时才做（当前不做）。
- **参考**：DataProtector `DpThreatEngine.c`（权重 / 30s 衰减 8 分 / 冷却减半 / 跨战术 +12 / 血缘 50% 传播 / 阈值 30-60-90-130）。

## ADR-010 服务端策略正文签名：已知未闭环

- **状态**：**待办**（安全工程整改，不在美化/借鉴落地范围）
- **背景**：Agent 侧 `policy_sign.go` 生产默认无公钥会拒策略，但 `backend/agent_sync.py` / `agent_edr.py` 直接输出 policy，**没有 `policy.sign.v1` 服务端签名实现**；全仓只有升级包签名与 notify HMAC。
- **影响**：策略验签链条在服务端侧缺一环；需确认 `setConfig` / `InsecureSkipVerify` 路径后补齐签名生成与密钥分发。
- **决策**：**本轮不擅自实现**——涉及密钥管理与协议变更，需独立安全评审与 Agent/服务端联调。仅在 `AGENTS.md` §6 与本报告登记，避免后续误判「验签已闭环」。
- **教训**：判断闭环必须交叉验证生成端与消费端，不能只看单侧代码。

## ADR-015 MITRE 版本演进用「独立可选文件」，默认零影响

- **状态**：已实现（2026-11-22）
- **决策**：`backend/data/mitre_techniques_cn.json`（52 条中文映射）保持不变；新增独立 `backend/data/mitre_versioning.json` 登记 `revoked_by / deprecated / data_sources / mitre_version / verified`，并设 `allowed_data_sources` 闭集。`technique_meta()` 合并暴露 `status(active/deprecated/revoked) / data_sources / label_plain`，子技术在自身未登记时继承父技术状态。
- **理由**（借鉴 wazuh `mitredb.py`）：ATT&CK 每年更新，技术会被撤销/废弃，缺版本字段以后难维护。但**不能臆造权威数据**——所以默认文件全空、`verified=false`，不改变任何现有技术的展示；把「字段模型 + 校验器 + 覆盖度分析能力」先建好，数据由维护者对照所用 ATT&CK 版本 change log 核实后再填。
- **后果**：`validate_rules.py` 增加 `validate_mitre_versioning()` 闭集校验（非法技术 ID / 非白名单数据源在导入期即报错，不静默生效）；`label` 在状态非 active 时带「已废弃/已撤销 → Txxxx」后缀，`label_plain` 保留原值供老消费者使用。
- **备选方案（否决）**：直接往中文映射文件里塞版本字段——会污染名称数据、让 52 条条目语义混杂，且难以区分「已核实」与「占位」。
